# 需求从0到1落地全流程（架构师视角）

> 本文档从架构师的视角，完整梳理一个需求从提出到上线复盘的全生命周期，每个阶段给出具体的动作、产出物、常见坑点和检查清单，可作为团队研发规范或个人 Checklist 使用。

---

## 1. 需求接收与澄清

### 1.1 需求来源

| 来源       | 特点          | 关注重点              |
| -------- | ----------- | ----------------- |
| 产品经理 PRD | 相对完整，有交互稿   | 是否有遗漏的异常流程        |
| 客户需求     | 口头/邮件为主，碎片化 | 需要反向整理成结构化文档      |
| 运营需求     | 时效性强，追求"快"  | 要警惕为了赶时间而牺牲扩展性    |
| 技术优化     | 无明确业务方，自驱动  | 需要量化收益（性能/成本/稳定性） |

### 1.2 澄清要点（架构师必须追问的 5 个问题）

1. **做什么 / 不做什么**：明确 MVP 边界，防止范围蔓延（Scope Creep）。用一句话写出"本次不做"的清单，比写"要做"的清单更重要。
2. **用户是谁**：C端/B端/内部系统？决定了并发量级、SLA 要求、权限模型。
3. **边界条件**：
    - 数据量级（1万 vs 1亿，架构完全不同）
    - 峰值 QPS / TPS
    - 数据一致性要求（强一致 vs 最终一致）
4. **异常处理**：
    - 第三方接口挂了怎么办
    - 用户重复提交怎么办
    - 数据回滚策略
5. **验收标准**：需求方如何验收？有没有明确的成功指标（如转化率提升X%、RT下降到Xms）。

**输出物**：《需求澄清纪要》（建议邮件/文档留痕，避免口头约定造成后期扯皮）。

## 2. 需求分析

### 2.1 输入-处理-输出（IPO 模型）

用这个模型强制自己把需求"翻译"成技术语言：

- **Input**：数据来源（用户输入、上游系统、定时任务、消息队列）、数据格式、数据校验规则
- **Process**：核心业务逻辑、涉及的状态流转、需要调用的内外部服务
- **Output**：返回给谁、什么格式（同步返回/异步通知）、是否需要落库/落缓存/发消息

### 2.2 场景拆分

|场景类型|示例|关注点|
|---|---|---|
|正常场景|用户正常下单|主链路是否清晰、性能是否达标|
|异常场景|库存不足、支付超时、第三方服务超时|是否有降级、重试、补偿机制|
|边界场景|并发抢购最后一件商品、参数为0/null/超长字符串|幂等性、并发控制、参数校验|

**建议产出**：用表格列出"场景 → 触发条件 → 期望结果"，作为后续测试用例的直接输入，做到需求分析和测试用例一次到位。

## 3. 技术方案设计

### 3.1 架构设计

- 画出**系统上下文图**：本次改动涉及哪些系统、上下游依赖关系
- 明确**分层设计**：Controller / Service / DAO 各层职责边界
- 考虑**技术选型**：是否需要引入新组件（MQ、缓存、搜索引擎），评估团队熟悉度和运维成本

### 3.2 表设计

- 字段类型是否合理（如金额用 decimal 而非 float）
- 索引设计：查询字段是否有索引，是否会出现索引失效
- 是否需要考虑**分库分表**（预估数据增长曲线）
- 预留字段/扩展字段策略，避免频繁 DDL

### 3.3 API 设计

- RESTful 规范 or RPC 接口规范统一
- 请求/响应参数是否做了版本兼容设计
- 幂等性设计（如订单创建接口用幂等 Token）
- 错误码规范（区分业务错误 vs 系统错误）

### 3.4 缓存设计

- 缓存什么（热点数据、计算结果）
- 缓存更新策略：Cache Aside / 主动失效 / 定时刷新
- 缓存穿透、击穿、雪崩的应对方案（布隆过滤器、互斥锁、过期时间打散）

### 3.5 异步设计

- 哪些环节可以异步化（发短信、发通知、数据同步）
- 消息队列选型和消费保证（at-least-once / exactly-once）
- 消息堆积、消费失败的重试和死信队列策略

**输出物**：《技术方案设计文档》，包含架构图、时序图、表结构 SQL、接口文档草稿。

## 4. 技术评审

评审的本质是"用别人的经验，提前发现自己看不到的坑"。评审时重点过一遍：

- **N+1 问题**：循环里是否有数据库/RPC调用，能否批量化
- **事务问题**：事务边界是否清晰，是否有大事务（长时间持锁）、跨库事务（分布式事务）
- **性能问题**：预估 QPS 下，接口 RT 是否达标；是否有慢查询风险
- **扩展性**：如果数据量翻10倍/业务方翻10倍，当前设计是否还能扛住
- **兼容性**：是否影响存量数据、是否有灰度/兼容期设计
- **安全性**：越权访问、SQL注入、敏感数据加密

**建议**：评审前把方案文档提前发出去，评审会控制在1小时内，聚焦"改动点+风险点"，而不是从头讲一遍需求。

## 5. 开发阶段

### 5.1 分层开发顺序

1. **DB**：先建表、写好索引，评审通过后再改
2. **DAO**：只做数据访问，不写业务逻辑
3. **Service**：核心业务逻辑层，事务在这一层控制
4. **Controller**：只做参数校验、组装、调用 Service，不写业务逻辑

### 5.2 常见问题清单

|问题|表现|解决方案|
|---|---|---|
|循环查库|for 循环里 select|批量查询（IN 查询）+ 内存 Map 关联|
|事务缺失|多个写操作没有事务包裹，部分成功部分失败|用 `@Transactional` 或分布式事务框架，注意事务传播机制|
|大对象返回|接口一次性返回几万条数据|分页、字段裁剪（不要 select *）|
|硬编码|魔法数字、写死的配置|提取配置中心/枚举|
|日志缺失|出问题排查不到|关键节点打印日志，注意脱敏|

**建议**：开发过程中自测先行，写完一个接口用 Postman/curl 先验证一遍正常场景和一个异常场景，再提交联调。

## 6. 测试阶段

- **单元测试**：核心业务逻辑覆盖率要求（如 Service 层覆盖率 > 70%），重点覆盖边界条件和异常分支
- **接口测试**：按第2步"场景拆分"表格逐条验证，覆盖正常/异常/边界场景
- **压力测试**：
    - 明确压测目标（QPS、RT、错误率）
    - 找到系统瓶颈（CPU/内存/DB连接池/线程池）
    - 压测环境尽量贴近生产（数据量级、机器配置）

**输出物**：测试报告，包含压测数据和性能瓶颈分析。

---

## 7. 上线

### 7.1 灰度发布

- 按机器灰度 / 按用户灰度 / 按流量比例灰度
- 灰度期间重点观察监控指标，设定观察时间窗口（如30分钟无异常再扩量）

### 7.2 回滚方案

- 代码回滚：确保上一版本可快速重新部署
- 数据回滚：如果涉及数据变更（如数据迁移），要提前准备回滚脚本
- 配置回滚：功能开关（Feature Toggle）优先，出问题一键关闭而不需要重新发布

### 7.3 配置检查清单

- [ ] 数据库连接串、密码是否为生产环境配置
- [ ] 定时任务是否在多实例下重复执行
- [ ] 限流、超时时间等参数是否符合生产预期
- [ ] 日志级别是否调整为合适级别（避免 DEBUG 刷爆磁盘）

---

## 8. 监控

上线不是终点，监控体系是保障系统稳定的最后一道防线。

|监控维度|指标|目的|
|---|---|---|
|流量|QPS/TPS|判断流量是否符合预期、是否有异常突增|
|性能|RT（平均值/P99/P999）|发现慢接口、性能劣化|
|稳定性|错误率、异常堆栈|快速定位故障|
|数据库|慢SQL、连接池使用率|提前发现数据库瓶颈|
|资源|CPU/内存/磁盘/网络|容量评估、扩容依据|

**建议**：为核心指标配置告警阈值和自动通知（如企业微信/钉钉机器人），做到"问题发生5分钟内感知"。

---

## 9. 复盘

上线稳定运行一段时间后，做系统性复盘，形成经验沉淀。

### 9.1 性能优化

- 是否有慢查询可以优化（加索引、SQL改写）
- 是否有可以异步化/批量化的地方
- 缓存命中率是否达标

### 9.2 架构优化

- 本次设计是否有过度设计或设计不足的地方
- 是否有可以沉淀为通用组件/中间件的部分
- 技术债务记录（这次为了赶进度做的妥协，后续要还的债）

### 9.3 代码优化

- Code Review 中发现的共性问题（如异常处理不规范、命名不清晰）
- 是否可以沉淀为团队编码规范或脚手架

**输出物**：《项目复盘报告》，包含"做得好的地方"、"问题与根因"、"改进行动项（负责人+时间点）"。

## 附：全流程一张图

```
需求接收 → 需求分析 → 技术方案设计 → 技术评审
    ↓
开发（DB→DAO→Service→Controller）
    ↓
测试（单测→接口测试→压测）
    ↓
上线（灰度→观察→全量，配好回滚方案）
    ↓
监控（QPS/RT/错误率/慢SQL 持续观察）
    ↓
复盘（性能/架构/代码优化，沉淀经验）
```

这个流程的核心思想是：**每个阶段都要有明确的输出物，且前一阶段的产出是后一阶段的输入**（例如需求分析阶段的场景拆分表，直接复用为测试用例；技术方案设计文档，直接作为评审的输入）。这样可以避免"文档是文档，代码是代码"的两张皮问题。
