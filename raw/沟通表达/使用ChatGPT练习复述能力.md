# 一、方法

沟通表能力主要拆分为3个能力：

> **输入 -> 理解  -> 组织  -> 输出**


## 万能表达公式

> **结论 → 原因 → 例子 → 总结**   【通用】


> **结论 → 原因 → 价值**   【通用】


以后遇到**成本问题**，尽量用这种表达：

> **前期投入是什么 → 换来了什么 → 后期节省了什么。**

例如：

> 前期需要投入时间搭建 Agent 框架和工具体系，但后续新增系统时，只需要扩展工具而不是重构流程，因此长期维护成本更低，系统扩展性也更好。

这一类表达在老板汇报、方案评审、技术面试里都非常加分。


## 二、练习对话QA例子

**面试官：**

>Q：你们的不良品根因追溯智能体，为什么要使用 Agent，而不是传统的"RAG + 大模型"方案？

请回答：

1. **Agent 和普通 RAG 的区别是什么？**
2. **为什么你们这个项目需要 Agent？**
3. **如果项目后期变复杂，Agent 能带来哪些优势？**


>A：

**结论：**  
我认为普通的 RAG 更适合解决知识问答问题，而我们的不良品根因追溯涉及多数据源查询和多步骤分析，因此更需要 Agent。

**区别：**  
RAG 的核心作用是从知识库中检索与问题相关的内容，再把这些内容提供给大模型生成答案。Agent 在此基础上，还能够根据任务规划执行步骤，并选择和调用相应的工具。

**项目适用性：**  
在不良品追溯场景中，智能体可能需要先查询生产批次，再关联设备、物料、工艺参数和质检记录。不同数据可能来自 ERP、MES、QMS 或知识库，单次检索无法完整解决问题，而 Agent 可以按照任务需要调用不同系统的接口并综合分析。

**后期价值：**  
随着系统和业务规则变多，Agent 可以通过增加工具和调整执行流程来扩展能力，不需要把所有业务路径都写成固定流程。因此，它更适合复杂、动态的追溯场景。不过 Agent 的成本和不确定性也更高，简单查询仍然可以直接采用 RAG，不需要所有问题都走 Agent。

**总结：**  
所以我们的方案不是用 Agent 完全替代 RAG，而是让 Agent 负责规划和工具调用，让 RAG 作为其中一个知识检索工具。




> Q：**既然 Agent 的调用成本更高、响应速度更慢，而且执行结果可能不稳定，为什么不把所有追溯流程都写成固定工作流？你如何判断一个问题应该走 Agent，还是走普通 RAG 或固定流程？**

回答时重点讲清楚：**判断标准、方案边界和成本控制**。


>A：

**结论：**

我认为并不是所有问题都应该交给 Agent，而应该根据任务复杂度选择不同的处理方式。

**第一种：普通查询**

如果只是查询知识库或固定文档，例如 SOP、设备说明等，通过 RAG 检索即可完成，这类场景速度快、成本低。

**第二种：复杂业务**

如果涉及多个系统的数据查询、多步分析或工具调用，例如需要同时查询 ERP、MES、QMS，再综合分析原因，那么更适合交给 Agent 来规划执行流程。

**为什么不用固定工作流？**

固定工作流适合业务稳定的场景。但制造业的业务系统和规则会不断变化，如果每增加一个系统都修改工作流，维护成本会越来越高。而 Agent 可以通过新增工具和调整执行策略来适应变化，扩展性更好。

**总结：**

因此，我认为最佳方案不是"全部用 Agent"，也不是"全部用工作流"，而是根据业务复杂度选择最合适的方案，让简单任务走 RAG，复杂任务走 Agent，这样能够兼顾效率、成本和扩展性。



> Q：**如果 Agent 调用了 ERP、MES、QMS 三个系统，但其中一个系统接口超时了，你会怎么设计，保证整个智能体不会因为一个接口失败就无法回答用户？**

这道题开始涉及**系统设计**了，不需要回答得很全面，我主要看你的分析思路。

> A：

**结论：**  
我会采用超时、重试、故障隔离和降级机制，避免某一个系统接口失败导致整个 Agent 任务失败。

**第一步，接口隔离：**  
ERP、MES 和 QMS 的调用分别设置独立超时时间，并尽量并行执行。某个接口超时时，不阻塞其他接口继续返回结果。

**第二步，有限重试和熔断：**  
对临时网络抖动可以进行一到两次重试；如果某个系统持续异常，则触发熔断，避免 Agent 反复调用并拖慢整个请求。

**第三步，判断数据重要性：**  
系统需要根据当前问题判断失败接口是否属于关键数据源。如果缺失数据不影响核心结论，可以基于其他数据继续回答；如果会影响根因判断，就只能输出初步分析，不能给出确定结论。

**第四步，透明降级：**  
返回结果时标明已获取的数据、缺失的数据以及可能造成的影响。例如提示用户：“MES 接口当前超时，本次结果仅基于 ERP 和 QMS 数据生成，设备与工艺参数尚未验证。”

**总结：**  
这样既能保证系统具备一定可用性，也能防止大模型在证据不足的情况下生成过度确定的结论。
