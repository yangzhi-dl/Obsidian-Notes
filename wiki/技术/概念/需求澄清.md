# 需求澄清

> 需求澄清是需求全流程的第一阶段，核心目标是用结构化方法把模糊的需求"翻译"成可执行的技术输入。

## 架构师必须追问的 5 个问题

1. **做什么 / 不做什么** — 明确 MVP 边界，防止范围蔓延（Scope Creep）。"不做"清单比"要做"清单更重要。
2. **用户是谁** — C端/B端/内部系统？决定并发量级、SLA 要求、权限模型。
3. **边界条件** — 数据量级（1万 vs 1亿）、峰值 QPS/TPS、数据一致性要求。
4. **异常处理** — 第三方接口挂了怎么办？用户重复提交？数据回滚策略？
5. **验收标准** — 明确的成功指标（转化率提升X%、RT下降到Xms）。

> **输出物**：《需求澄清纪要》——邮件/文档留痕，避免口头约定造成后期扯皮。

## IPO 模型（Input-Process-Output）

用这个模型把需求"翻译"成技术语言：

| 维度          | 关注点                               |
| ----------- | --------------------------------- |
| **Input**   | 数据来源（用户输入/上游系统/定时任务/MQ）、数据格式、校验规则 |
| **Process** | 核心业务逻辑、状态流转、内外部服务调用               |
| **Output**  | 返回给谁、什么格式（同步/异步）、是否落库/缓存/发消息      |

## 场景拆分

| 场景类型 | 关注点 |
|----------|--------|
| **正常场景** | 主链路是否清晰、性能是否达标 |
| **异常场景** | 是否有降级、重试、补偿机制 |
| **边界场景** | 幂等性、并发控制、参数校验（null/超长/0值） |

> 场景拆分表可直接复用作测试用例——做到需求分析和测试用例一次到位。

## 需求来源与关注点

| 来源 | 特点 | 重点关注 |
|------|------|----------|
| 产品经理 PRD | 相对完整，有交互稿 | 是否有遗漏的异常流程 |
| 客户需求 | 口头/邮件为主，碎片化 | 反向整理成结构化文档 |
| 运营需求 | 时效性强，追求"快" | 警惕牺牲扩展性 |
| 技术优化 | 无明确业务方，自驱动 | 量化收益（性能/成本/稳定性） |

## 核心原则

- **输出物驱动**：每次澄清必须有书面纪要留痕
- **向前兼容**：场景拆分表直接嵌入后续测试环节
- **边界优先**：先搞清楚不能做什么，再确定要做什么
