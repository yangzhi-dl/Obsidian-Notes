# 技术评审清单

> 评审的本质是"用别人的经验，提前发现自己看不到的坑"。评审的重点不是从头讲需求，而是聚焦"改动点+风险点"。

## 6 大检查维度

### 1. N+1 问题
- 循环里是否有数据库/RPC 调用？
- 能否批量查询 + 内存 Map 关联？

### 2. 事务问题
- 事务边界是否清晰？
- 是否有大事务（长时间持锁）？
- 是否有跨库事务（分布式事务方案）？
- `@Transactional` 传播机制是否正确？

### 3. 性能问题
- 预估 QPS 下接口 RT 是否达标？
- 是否有慢查询风险（`select *`、无索引查询）？
- 是否需要分页 / 字段裁剪？

### 4. 扩展性
- 数据量翻10倍，当前设计是否还能扛住？
- 业务方翻10倍，架构是否需要重构？
- 是否预留了扩展字段 / 策略模式？

### 5. 兼容性
- 是否影响存量数据？
- 是否有灰度 / 兼容期设计？
- API 是否有版本兼容方案？

### 6. 安全性
- 是否存在越权访问（水平/垂直越权）？
- SQL 注入风险？
- 敏感数据是否加密存储/传输？

## 评审流程建议

1. **提前发送方案文档** — 评审前 24h 发出，与会者提前阅读
2. **控制时长** — 评审会控制在 1 小时内
3. **聚焦焦点** — 只讨论"改动点 + 风险点"，不从头讲需求

## 常见问题速查

| 问题 | 表现 | 解决方案 |
|------|------|----------|
| 循环查库 | for 循环里 select | 批量查询 + 内存 Map 关联 |
| 事务缺失 | 多个写操作没有事务包裹 | `@Transactional` + 注意传播机制 |
| 大对象返回 | 一次性返回几万条数据 | 分页、字段裁剪（不要 select *） |
| 硬编码 | 魔法数字、写死的配置 | 提取配置中心 / 枚举 |
| 日志缺失 | 出问题排查不到 | 关键节点打印日志，注意脱敏 |
