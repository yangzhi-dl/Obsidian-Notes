# 项目复盘

> 上线稳定运行一段时间后，做系统性复盘，形成经验沉淀。复盘不是追责，而是**让团队从自己的经验中学习**。

## 三维度复盘法

### 1. 性能优化
- 是否有慢查询可以优化（加索引、SQL 改写）？
- 是否有可以异步化 / 批量化的地方？
- 缓存命中率是否达标？

### 2. 架构优化
- 本次设计是否有过度设计或设计不足？
- 是否有可以沉淀为**通用组件 / 中间件**的部分？
- **技术债务记录**：为了赶进度做的妥协，后续要还的债

### 3. 代码优化
- Code Review 中发现的共性问题（异常处理不规范、命名不清晰）
- 是否可以沉淀为团队编码规范或脚手架？

## 输出物：《项目复盘报告》

```
项目复盘报告
├── 做得好的地方（What went well）
├── 问题与根因（What went wrong + Root Cause）
└── 改进行动项（Action Items）
    ├── 负责人
    └── 完成时间点
```

## 复盘 vs 总结

| 维度 | 普通总结 | 深度复盘 |
|------|----------|----------|
| 视角 | 发生了什么 | 为什么发生 |
| 深度 | 结果描述 | 根因分析 |
| 产出 | 流水账 | 可复用的经验/检查项 |
| 行动 | 知道了 | 改进了（有负责人+DDL） |

## 核心原则

- **不追责**：复盘聚焦系统性问题而非个人失误
- **可行动**：每个发现都必须对应具体改进行动项
- **可沉淀**：优化项应转化为规范 / 脚手架 / CheckList
